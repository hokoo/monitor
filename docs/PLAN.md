## Порядок и граница доставки

Порядок: T1 → T2 → T3 → T4 → T5 → T6. T3–T5 технически опираются на T1–T2 и могут исследоваться независимо, но реализация в общем checkout выполняется последовательно. Неопределённость отдельного провайдера не должна блокировать независимую готовую работу после разрешения на выполнение.

Первый полезный срез — несколько аккаунтов Codex после T3. Полная первая версия требует выполнения всего согласованного покрытия и приёмки T6. Значение `unsupported` не заменяет выполненную интеграцию; изменение объёма фиксируется отдельным решением пользователя.

Общий DoD кодовых задач: выполнены AC, пройдены целевые проверки, просмотрен фактический diff, результат и ограничения зафиксированы в checkpoint соответствующей задачи, изменения закоммичены локально. Push, merge и публикация не входят в границу доставки. Команды проверок определяются после выбора стека и записываются вместе с фактическими результатами; непроведённая проверка не считается успешной.

После разрешения на выполнение нескольких задач применяется delivery-owner: root → свежий batch_owner → worker и при необходимости test_monitor. Один владелец пакета и один автор изменений одновременно; root принимает завершённый пакет до следующего. Перед закрытием всей первой версии проводится независимая epic_qa. Планирование и этот первый коммит не запускают данный процесс.

**Время и опрос.** `receivedAt` = время получения ответа сервером монитора; `observedAt` = время измерения у провайдера, только если источник его явно сообщает; иначе для активного запроса допустимо `receivedAt` с пометкой `observationBasis: response_received`. Для агрегированного отчёта `bucket end` и `data_refreshed_at` сохраняются отдельно: полученный сейчас старый отчёт не становится текущим остатком. Для status line/другого пассивного снимка сохраняется только подтверждённый timestamp создания самого снимка; время чтения или `mtime` без контракта записи не сдвигает `observedAt`. Повторное чтение неизменного снимка — проверка наличия, не новое наблюдение. Если timestamp отсутствует, возраст неизвестен и состояние `unknown/stale`, а не `fresh`.

**10 секунд** — базовая техническая частота попыток активных источников, а не разрешённая провайдером частота: ни один просмотренный источник не гарантирует read каждые 10s. В T2 scheduler может тикать каждые 10s, но адаптер задаёт минимум конкретного источника после проверки его условий в T3–T5; `Retry-After`, backoff, 401/403 и незавершённая попытка имеют приоритет. Для аналитики с часовым запаздыванием и дневными bucket 10s не улучшают данные: разумный **кандидат** — 5 минут для отчётов и 180s TTL лишь для оперативных snapshot, но эти значения не следует выдавать за правило провайдера до проверки. Для Claude status line 10s — только проверка снимка. Браузер может обновлять возраст каждую секунду без нового обращения к провайдеру. `nextAttemptAt`, `retryAfter`, причина задержки и фактический `observedAt` видны в подробностях. При достижении reset время прежний остаток устаревает до нового ответа.

**DG3 — точное недостающее решение.** Официально подтверждены исторические расходы OpenAI и Claude, а для Z.ai — отделение Standard API от Coding Plan; текущие остатки денежных кредитов/доступных квот всех трёх API из исследованных публичных контрактов и имеющихся прав не подтверждены. **Минимальный стек и контракт T2.** Node.js 24.13.1 (проверен root), встроенные `node:http`, `node:fs`, `fetch`, `node:test`, HTML/CSS/JS без сборки и БД; не устанавливать SDK для модельных запросов. Один процесс на loopback, один scheduler, кэш в памяти, статические файлы и JSON API. Серверный config: `locale`, упорядоченные `accounts[]` с уникальным `id`, `provider`, `label`, `sources[]` (`id`, `type`, `authRef` только серверная ссылка); источник регистрируется явным ключом, конфиг не загружает код. Ключ кэша/задачи = `(account.id, source.id)`, ключ метрики = `(account.id, source.id, metric.key, window.id|null)`; изоляция ошибок и расписания на тот же ключ. `readSource(account, source, {signal})` возвращает нормализованные `metrics[]` и метаданные наблюдения либо безопасную ошибку; адаптер не управляет глобальной рабочей авторизацией. Метрика: `kind`, `scope`, `unit`/`currency` nullable, `value` nullable (ноль значим), `window` nullable (`id`, `durationMinutes`, `resetsAt`), `observedAt` nullable, `observationBasis`, `receivedAt`, `sourceLabel`. Источник: `lastAttemptAt`, `lastSuccessAt`, `nextAttemptAt`, `retryAfter`, `staleAfter`, `status`, `safeError`. Для пассивных/агрегированных источников отдельно `snapshotAt`, `periodStart/End`, `dataRefreshedAt` nullable. Поля времени ISO UTC в API монитора; timestamp провайдера переводится с сохранением семантики, никогда не подменяется локальным временем чтения. Секреты не выходят из серверных ссылок; JSON браузеру содержит только безопасные поля. T2 использует демонстрационные адаптеры, реальные источники подключаются в T3–T5 без изменения UI. Это рабочий технический контракт, не утверждение схем провайдеров.
