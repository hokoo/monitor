# Спецификация монитора ресурсов

Статус: проект спецификации v0.1. Дата: 2026-10-29.

Приложение собирает остатки лимитов и другие показатели ресурсов в одном веб-интерфейсе в стиле TUI. Основной сценарий: открыть экран и понять, какие ресурсы доступны, когда восстановятся лимиты и насколько свежи показанные значения.

Спецификация описывает первую версию. Выполнение задач T1–T6 авторизовано 2026-11-09; неподтверждённые интеграции остаются открытыми решениями, а не обещанием доступности данных.

## 1. Требования и исходные допущения

Подтверждено пользователем:

- Веб-интерфейс с визуальным стилем TUI, не терминальное приложение.
- Цветной TUI; визуальные ориентиры — терминальные интерфейсы Codex, OpenCode и Claude.
- Английский интерфейс по умолчанию с доступной русской локализацией.
- Codex, Claude и GLM на Z.ai.
- Несколько учёток для любого типа ресурса: подписок, API и будущих интеграций, независимо от провайдера.
- Поддержка как подписок, так и API: остатки лимитов, доступные балансы и квоты.
- Обязательное отображение 5h-лимитов, если они применяются к конкретной учётке, вместе с остальными применимыми окнами.
- Базовый интервал опроса источников — 10 секунд.
- Возможность впоследствии добавлять другие состояния и источники.
- Минимальная реализация по принципам ponytail.
- Язык задаётся только серверным конфигом (`locale: en` по умолчанию, также `ru`), применяется после перезапуска. Переключателя языка в браузере нет.
- Один пользователь, Linux, современный настольный браузер, доступ только через loopback.

Предлагаемые настройки первой версии, пока не отдельные согласованные требования:

- Одна страница; аккаунты и источники задаются локальным конфигурационным файлом.
- Работа только пока запущен процесс приложения; без отдельного фонового сервиса.

Доступные аккаунты по сообщению пользователя: два GPT, один GLM на Z.ai и один бесплатный Claude. Тарифы GPT и GLM, доступность Codex, API-проекты, ключи и права чтения показателей пока не установлены. Наличие пользовательского аккаунта не подтверждает API-доступ или доступ к данным лимитов.

Для GLM и Claude второй реальной учётки сейчас нет. Это ограничивает живую проверку нескольких аккаунтов, но не отменяет требования их поддержки. Две учётки GPT — кандидаты для первой проверки; их применимость к нужным источникам подтверждается в T1.

## 2. Объём первой версии

Входят: список аккаунтов, отдельные строки ресурсов и окон лимитов, актуальные значения и время сброса, обновление, фильтрация, диагностика ошибок и отметка свежести. Несколько аккаунтов обязательны для каждого поддерживаемого типа ресурса и провайдера. Это требование распространяется и на будущие интеграции.

Поддержка API означает отдельные показатели соответствующего API-аккаунта или проекта. Для Codex предполагается OpenAI API; его связь с конкретной подпиской ChatGPT и доступность показателей нужно установить в исследовании. Одинаковый email не является доказательством общей квоты или баланса.

Приоритет API-метрик — баланс/кредиты и остатки доступных квот. Расходы показываются отдельно, если доступны; бюджеты требуют подтверждения семантики. RPM/TPM не входят в обязательный объём первой версии без отдельного запроса. Конкретный обязательный набор по каждому провайдеру фиксируется по результатам T1.

Бесплатный Claude входит в исследуемый объём. Тип источника `subscription` обозначает лимиты пользовательского плана, в том числе бесплатного, если их можно получить. Возможности платного плана или Claude Code не переносятся на бесплатный аккаунт по предположению. Если источник для него недоступен, требуется отдельное решение о покрытии; покупка подписки не подразумевается.

Не входят: история и графики расхода, прогноз исчерпания, уведомления, автоматическое переключение аккаунтов, отправка запросов моделям, покупка кредитов, сброс квот, удалённый хостинг, собственная система пользователей, маркетплейс плагинов. Подключение новых типов ресурсов — последующие задачи, а не набор пустых интеграций в первой версии.

## 3. Пользовательские сценарии

1. Пользователь задаёт аккаунтам понятные имена и указывает источники авторизации. Запускает приложение и открывает локальный адрес.
2. На экране видны все настроенные аккаунты, включая те, по которым пока нет данных или возникла ошибка.
3. Пользователь сравнивает остатки и время сброса по каждому окну. API-баланс и лимиты подписки показаны раздельно.
4. Пользователь фильтрует строки по провайдеру, имени аккаунта или ресурсу и при необходимости обновляет данные вручную.
5. При сбое пользователь видит последнее успешное значение с возрастом и ошибкой обновления либо явное отсутствие данных.
6. Для любого типа ресурса пользователь добавляет ещё один аккаунт в конфигурацию без изменения кода и видит оба одновременно. Новый провайдер требует небольшого модуля интеграции с поддержкой нескольких аккаунтов; существующий экран переиспользуется, если тип метрики уже поддерживается.

## 4. Экран и взаимодействие

Экран содержит название приложения, состояние обновления, фильтр, таблицу ресурсов и доступную с клавиатуры область подробностей выбранной строки.

Колонки таблицы:

| Колонка | Содержание |
| --- | --- |
| Аккаунт | Провайдер и пользовательское имя, без обязательного раскрытия email |
| Ресурс | Подписка/API, название показателя, окно или область действия |
| Остаток / значение | Процент, количество, сумма с валютой или текстовое состояние |
| Сброс | Время до сброса; точная дата и часовой пояс в подробностях |
| Получено | Возраст последнего успешного наблюдения этой строки |
| Состояние | Загрузка, актуально, устарело, нужна авторизация, ошибка, не поддерживается |

В подробностях: человекочитаемый источник, единица измерения, область действия (аккаунт, организация, проект или модель), точное время наблюдения и последней попытки, безопасное описание ошибки. Секреты, сырые ответы авторизации и приватные пути не показываются.

Оформление: цветной TUI в духе терминальных интерфейсов Codex, OpenCode и Claude. Основа — тёмный фон, моноширинный системный шрифт, компактные строки, тонкие рамки и разделители, текстовые индикаторы и подсказки клавиш вида `[r] Refresh`. Цвет используется для статусов, полос остатков, заголовков, фокуса и выделения активной строки. Эти продукты задают визуальное направление; точное копирование конкретной темы не требуется. Шрифт и ресурсы интерфейса загружаются локально.

Предлагаемая семантика палитры: светлый основной текст, приглушённые вторичные подписи, cyan/blue для действий и фокуса, зелёный для успешного получения данных, amber для устаревших данных и необходимости авторизации, красный для ошибок, нейтральный серый для неизвестных и неподдерживаемых значений. Цвет успешного получения не означает большой остаток квоты. Неизвестный или устаревший остаток не получает оформление актуального значения.

Полоса процентов дополняет число, цвет статуса — текстовую подпись или символ. Активная строка выделяется фоном и маркером. Текст, фокус и индикаторы сохраняют читаемый контраст; смысл экрана остаётся понятным без различения цветов. Конкретные оттенки задаются общими CSS-переменными при реализации T2.

Управление: кнопка `Refresh` («Обновить»), поле фильтра, `r` для обновления, `/` для фокуса фильтра, `Esc` для его очистки. Сокращения не срабатывают при вводе в поле и с системными модификаторами. Все действия доступны через Tab, фокус видим. На узком экране таблицу можно прокручивать без потери доступа к управлению.

Порядок строк стабилен: порядок аккаунтов в конфигурации, затем ресурсы источника. Обновление не меняет выбор и фильтр. Пустая конфигурация показывает инструкцию подключения, пустой результат фильтра — сообщение `No results` («Ничего не найдено»).

Язык определяется параметром `locale` серверного конфига: `en` по умолчанию или `ru`. Язык браузера и browser storage на выбор не влияют. Изменение применяется после перезапуска сервера и обновления страницы; горячая перезагрузка конфигурации не требуется. Перезапуск подчиняется общему правилу сброса кэша в памяти. Язык документа HTML и доступные названия элементов соответствуют выбранной локали.

Локализуются все собственные тексты интерфейса: заголовки, действия, состояния, подсказки, пустые экраны и сообщения об ошибках. Даты, числа и длительности форматируются по выбранной локали; валюта и часовой пояс не меняются из-за переключения языка. Имена аккаунтов, названия провайдеров, моделей и исходные названия неизвестных метрик не переводятся автоматически. Русские названия колонок и состояний в этой спецификации описывают смысл; основной интерфейс использует их английские эквиваленты.

Для первой версии достаточно небольших словарей `en` и `ru` с общими ключами и встроенных средств форматирования браузера. При отсутствующем переводе используется английский текст, а не внутренний ключ. Полнота обоих словарей проверяется при приёмке; резервный английский текст не заменяет обязательную русскую локализацию.

## 5. Семантика метрик

Подписка, денежный баланс, расход бюджета и ограничения скорости запросов не взаимозаменяемы. Каждый показатель сохраняет собственные единицы и область действия. Лимиты разных аккаунтов и провайдеров не суммируются.

- Процент остатка вычисляется как `100 − used_percent`, только если источник подтверждает семантику использованного процента и допустимый диапазон 0–100.
- Остаток количества вычисляется из `limit − used`, только если значения относятся к одной единице, области и периоду. Перерасход показывается явно; его нельзя скрыть искусственным нулём.
- Баланс показывается с валютой источника, без конвертации. Расход показывается как расход, даже если баланс недоступен.
- Число запросов или токенов не преобразуется в остаток подписки без подтверждённых правил провайдера.
- Неизвестное значение отображается как `—`, настоящий ноль — как `0`. Безлимитность показывается только при явном подтверждении источником.
- Окна лимитов определяются ответом источника, а не общим жёстким списком «5 часов / неделя».
- Применимое к учётке пятичасовое окно отображается отдельной строкой `5h` с остатком, временем сброса и свежестью данных. Оно не заменяется недельным или месячным лимитом; все применимые окна показываются одновременно. Применимость определяется для каждой учётки по данным источника или подтверждённым условиям её плана, а не по имени провайдера.
- Если 5h-лимит заведомо неприменим, строка не создаётся. Если он применим, но значение недоступно, показывается `—` с причиной либо последнее значение с отметкой устаревания. Отсутствие поля в ответе само по себе не доказывает неприменимость: неопределённость явно обозначается в состоянии источника.
- Наступление времени сброса не создаёт новый остаток автоматически. До свежего ответа прежнее значение считается устаревшим.
- Неверный формат или диапазон даёт ошибку данных, а не правдоподобное исправленное значение.

## 6. Минимальный контракт данных

Это логический контракт, а не утверждённая схема API или набор классов. Реализация использует простые структуры данных и функции.

| Объект | Обязательные сведения |
| --- | --- |
| Аккаунт | Стабильный локальный `id`, `provider`, `label`, настроенные типы источников, ссылки на авторизацию |
| Источник аккаунта | Идентификатор, тип `subscription` или `api`, статус, время последней попытки, безопасная ошибка |
| Метрика | Стабильный ключ внутри источника, название, вид, единица, область действия, значение или явное отсутствие |
| Окно | Идентификатор/название периода, длительность и время сброса, когда известны |
| Наблюдение | Время получения, время измерения источником при наличии, срок актуальности, ссылка на источник |

Начальные виды метрик: процент остатка, количественная квота, денежный баланс, расход/бюджет, текстовое состояние. Необязательные поля допускают отсутствие; неизвестное не заменяется нулём. Секреты не входят в нормализованную модель.

Статус получения данных отделён от свежести последнего значения. Например, при ошибке авторизации ранее полученный остаток остаётся видимым, но помечается как устаревший. У источника без метрик всё равно есть строка состояния: аккаунт не исчезает из таблицы.

Успешный частичный ответ обновляет только подтверждённые метрики. Ранее известное, но отсутствующее поле не получает новую дату свежести; оно сохраняется как устаревшее либо удаляется, если источник явно подтвердил, что ресурс больше не существует.

## 7. Интеграции и авторизация

| Провайдер | Подписка | API | Что требуется подтвердить |
| --- | --- | --- | --- |
| Codex / OpenAI | Документированный `account/rateLimits/read` через Codex app-server; доступ двух аккаунтов не проверен | Документированы исторические расходы организации; текущий баланс/остаток квоты не подтверждён | Изоляцию нескольких учёток, совместимость установленной версии, API-метрики и права |
| Claude | Free имеет 5h-лимит; его программное чтение не подтверждено, Claude Code status line не доказана для Free | Исторические API usage/cost документированы; текущий баланс/остаток квоты не подтверждён | Источник для Free, получение свежих данных без активной сессии, права, отдельный способ API-доступа |
| Z.ai | Официальный ZCode показывает квоты GLM Coding Plan; контракт чтения сторонним клиентом не подтверждён | Баланс/квоты Standard API не подтверждены публичным контрактом чтения | Конкретные интерфейсы получения и авторизацию для обоих типов |

Документированные основания:

- [Codex app-server](https://learn.chatgpt.com/docs/app-server#6-rate-limits-chatgpt) описывает чтение лимитов, процент использования и время сброса. Наличие метода не подтверждает готовую изоляцию нескольких учёток в нашем приложении.
- [Claude Free](https://support.claude.com/en/articles/8114491-get-started-with-claude) имеет пятичасовой лимит; [Claude Code status line](https://code.claude.com/docs/en/statusline) описывает данные окон, но [Claude Code включён в платные планы/API](https://support.claude.com/en/articles/14554922-claude-code-user-faq), а повторный запуск status line не обеспечивает новое наблюдение.
- [Claude API analytics](https://platform.claude.com/docs/en/manage-claude/usage-cost-analytics-api) описывает исторические расходы и usage с `data_refreshed_at`, но не текущий остаток кредита.
- [ZCode Usage Stats](https://zcode.z.ai/en/docs/usage-stats) описывает отображение квот Coding Plan Z.ai; [GLM Coding Plan](https://docs.z.ai/devpack/overview) устанавливает 5h и weekly credit pools. Эти страницы не устанавливают контракт API для стороннего монитора.

Предпочтение: документированный интерфейс или структурированные данные официального клиента. Парсинг экранов, браузерная автоматизация и недокументированные endpoint'ы не входят в базовое решение; если без них требование недостижимо, сначала фиксируются ограничение и выбор подхода.

Для каждого провайдера и типа ресурса требуется подтвердить изоляцию нескольких учёток. У каждого аккаунта своя привязка авторизации. Ключи метрик, кэш, ошибки и расписание обновления учитывают идентификаторы аккаунта и источника; аккаунты одного провайдера не перезаписывают данные друг друга. Монитор не переключает активный аккаунт рабочих CLI и не перезаписывает их настройки. Способ получения и обновления токенов выбирается после проверки официальных механизмов; конкурирующее обновление одной сессии монитором и CLI недопустимо.

API-ключ не считается автоматически достаточным для чтения финансовых показателей. При недостаточных правах интерфейс сообщает причину и нужный тип подключения, не просит расширенные права наугад. Наличие `unsupported` корректно описывает ограничение, но само по себе не закрывает требование интеграции.

## 8. Обновление и отказоустойчивость

Базовый интервал опроса активных источников — 10 секунд. Более редкий опрос допускается при подтверждённых ограничениях конкретного источника, `Retry-After` или задержке повторов после ошибки; причина и время следующей попытки доступны в подробностях источника. Для пассивных источников этот интервал означает проверку наличия нового снимка, а не гарантию обновления данных провайдером.

Предлагаемые остальные настройки: тайм-аут попытки 10 секунд, предельный возраст наблюдения 180 секунд. Срок 180 секунд предварительный и требует обоснования для каждого источника в T1. Настройки хранятся централизованно; ограничения источников, тайм-ауты и правила свежести уточняются в T1. Частота опроса и срок актуальности данных задаются отдельно.

- Первый сбор начинается при запуске сервера. Обновление браузера и дополнительные вкладки не создают независимые циклы опроса провайдеров.
- Одновременно выполняется не больше одной попытки на источник аккаунта. Если к очередному запуску предыдущая попытка не завершилась, запуск пропускается без постановки в очередь. Повторные клики также не создают очередь одинаковых запросов.
- Медленный или сломанный источник не задерживает результаты остальных; число одновременных запросов ограничено.
- Ручное обновление действует на все настроенные источники, независимо от фильтра, и соблюдает задержки провайдера.
- При `429` учитывается `Retry-After`; при сетевых ошибках применяется ограниченное увеличение интервала повторов. Ручная кнопка не обходит ограничения.
- После отказа авторизации автоматические попытки этого источника приостанавливаются до явной повторной попытки или переподключения. Другие аккаунты продолжают работать.
- Неудачная попытка сохраняет предыдущее значение и отмечает его как устаревшее. Истечение срока актуальности или времени сброса также делает значение устаревшим.
- Для пассивного источника повторное чтение того же снимка не обновляет время наблюдения. Время изменения файла не заменяет время измерения без подтверждённого контракта записи.
- Кэш первой версии находится в памяти. После перезапуска до первого результата показывается загрузка, а не выдуманный сохранённый остаток.

## 9. Устройство приложения и защита данных

Один серверный процесс обслуживает статический интерфейс, собирает источники и отдаёт нормализованные снимки. Браузер опрашивает локальный сервер обычными HTTP-запросами. WebSocket, очередь сообщений и база данных для первой версии не нужны.

Предлагаемый интерфейс — HTML/CSS/JS без фреймворка. Язык сервера и необходимые зависимости выбираются в T1 после проверки интеграций. Это решение не должно тянуть SDK для выполнения модельных запросов, если для чтения данных он не требуется.

Новая интеграция добавляет модуль получения данных и регистрацию в явном списке. Общий интерфейс работает с метриками и не разбирает ответы провайдеров. Неизвестный вид метрики отображается безопасным текстом или как неподдерживаемый; подключаемый исполняемый код из конфигурации не допускается.

Сервер слушает только loopback, проверяет допустимый Host и не открывает CORS внешним сайтам. Действия обновления требуют проверки origin; внешняя страница не должна получить данные или управлять монитором через localhost. Удалённая публикация требует отдельной модели доступа.

Токены остаются на серверной стороне. Конфигурация ссылается на согласованные локальные хранилища или переменные окружения. Секреты не попадают в Git, URL, аргументы команд, ответы браузеру или логи. Ошибки очищаются от токенов и чувствительного содержимого до сохранения и отображения. Данные провайдеров выводятся как текст, не исполняемый HTML.

## 10. Приёмка первой версии

Ниже перечислены обязательные проверки, а не уже полученные результаты:

- [ ] Для каждого поддерживаемого сочетания провайдера и типа ресурса проверены минимум две разные учётки одновременно; их принадлежность и показания сверены с источниками без изменения рабочей авторизации CLI.
- [ ] Обновление, ошибка и повторная авторизация одной учётки не смешивают и не перезаписывают данные другой учётки того же провайдера и типа ресурса.
- [ ] Для Codex/OpenAI, Claude и Z.ai проверены отдельно подписка и согласованный набор API-метрик. Исключение фиксируется как изменение объёма, а не как выполненная интеграция.
- [ ] Известные значения совпадают с источником с учётом округления, времени наблюдения и области действия.
- [ ] Проверены ноль, неизвестное значение, частичный ответ, перерасход, отсутствие окна и наступление времени сброса.
- [ ] Для учётки с применимым 5h-лимитом показаны его остаток и доступное время сброса отдельно от других окон. Проверены одновременно учётки с 5h-лимитом и без него, а также применимое окно без данных; отсутствие поля не трактуется как отсутствие лимита.
- [ ] Проверены тайм-аут, отсутствие сети, `401/403`, `429` и некорректный ответ. Другие источники продолжают обновляться.
- [ ] Ошибка обновления и пассивный снимок не выдают старые значения за свежие. Несколько вкладок не умножают опрос провайдеров.
- [ ] При штатной работе опрос источников запускается каждые 10 секунд без перекрывающихся попыток на один источник аккаунта. Проверены соблюдение `Retry-After`, задержки повторов и отображение причины увеличенного интервала.
- [ ] Фильтр, обновление, подробности и навигация работают с клавиатуры; смысл состояний понятен без цвета.
- [ ] Экран оформлен как цветной TUI: моноширинная сетка, компактные строки, рамки, цветные статусы и полосы, заметный фокус и активная строка. Проверены читаемость основной и приглушённой типографики, контраст и различимость ошибок, устаревших и неизвестных данных.
- [ ] Язык интерфейса задаётся только серверным конфигом: `en` по умолчанию и `ru`. После изменения конфига, перезапуска сервера и обновления страницы локализованы все собственные тексты и форматирование. Переключателя в браузере нет; язык браузера не переопределяет конфиг. Обе локали проверены на полноту, доступность и отсутствие обрезанных элементов.
- [ ] Секреты отсутствуют в Git, браузерных ответах и логах; внешнее происхождение запросов отклоняется.
- [ ] Есть инструкция запуска и пример конфигурации без секретов; добавление ещё одного аккаунта не требует правки кода.

Для нетривиальных преобразований и переходов состояния нужны небольшие автоматические проверки на обезличенных ответах, включая ошибочные. Реальные аккаунты используются для сверки интеграций, а не как обязательная зависимость каждого локального запуска тестов. Команды проверок фиксируются после выбора стека; отсутствие доступа не считается успешной проверкой.

Текущий пробел приёмки: для GLM и Claude нет второй реальной учётки; API-доступ по всем провайдерам пока не подтверждён. Проверки изоляции на обезличенных данных выполняются независимо, но не закрывают требование живой проверки двух учёток. Полная приёмка остаётся незавершённой до получения недостающих свидетельств либо явного согласования исключения с зафиксированным риском. Такое исключение не считается успешной технической проверкой и сейчас не согласовано.

## 11. Открытые решения и связь с планом

Состояние decision gates после обсуждения:

| Gate | Состояние | Решение или следующий шаг |
| --- | --- | --- |
| DG1 — язык | Закрыт | Только серверный конфиг, `en/ru`, применение после перезапуска |
| DG2 — запуск | Закрыт | Linux, localhost, один пользователь |
| DG3 — API-метрики | Направление принято, точное покрытие открыто | Приоритет баланса/кредитов и квот; матрица источников и прав в T1 |
| DG4 — ограниченные источники | Условный gate | Сначала исследование, затем отдельное решение по провайдеру, если нужны недокументированные запросы или пассивные данные |
| DG5 — несколько реальных учёток | Открыт для полной приёмки | Доступны 2 GPT, 1 GLM, 1 бесплатный Claude; недостающие проверки не подменяются фикстурами |

Инвентаризация аккаунтов не мешает начать исследование T1. Доступность конкретных источников, тарифы, API-права и изоляция авторизации ещё не проверены; они не считаются ни подтверждёнными возможностями, ни доказанным техническим тупиком. Выбор серверного языка, CSS-палитры и структуры файлов — решения реализации, а не отдельные пользовательские gates.

| Решение | Когда закрыть | Влияние |
| --- | --- | --- |

Каждая интеграция T3–T5 обязана поддерживать несколько учёток для подписок и API; T1 проверяет способы их изоляции, T2 обеспечивает общий контракт, T6 проверяет все сочетания.
